2.	Project Background
Current Problem
Hostel room allocation at most institutes is still handled through a mix of spreadsheets, physical application forms, notice boards and manual verification by the hostel office. Every year, the same steps are repeated by hand: collecting applications, checking eligibility, deciding who gets which room, and updating registers when someone requests a change. This makes the process slow, hard to track, and prone to errors such as double allocation of a bed or outdated occupancy records. Students often have no visibility into how a decision was made or what the status of their application is, which leads to confusion and repeated visits to the hostel office.
Proposed Solution
HostelAlloc will bring the entire hostel allocation cycle onto a single platform — from students submitting their accommodation applications, to the hostel office reviewing and running the allocation, to students receiving their room details and being able to raise room-change requests. The goal is to replace scattered manual records with one system that everyone (students, wardens and administrators) can rely on. 

3.	Project Vision
HostelAlloc aims to give students and hostel administrators a transparent, reliable and easy-to-use platform for requesting, allocating and managing hostel accommodation, reducing manual paperwork and making the whole process easier to track.
4.	Problem Statement
Institutes with residential hostels need to allocate a limited number of rooms among a much larger number of applying students every academic year, based on criteria such as year of study, category or seniority. When this is done manually, the process is time-consuming for the hostel office, offers little transparency to students, and makes it difficult to maintain an accurate, up-to-date record of who is occupying which room. It also makes handling room-change requests and tracking vacancies unnecessarily cumbersome. HostelAlloc is proposed as a software solution that manages the complete allocation lifecycle through a single, centralized system.

10.	To maintain role-based access control for students, wardens and administrators.

Scenario, Use Case and Activity Modelling
1. Objective
This assignment extends the Requirements Specification (SRS v1.0) prepared for HostelAlloc in Lab Assignment 2 by developing scenarios and UML models for the system. The same three detailed use cases selected in Assignment 2 - UC-004 (Submit Application), UC-006 (Run Allocation) and UC-011 (Approve/Reject Room-Change Request) - are carried forward and used consistently throughout this assignment.

●	2. Scenarios
A brief scenario is presented below for each of the three detailed use cases carried forward from Assignment 2.
2.1. Scenario 1 - UC-004: Submit Application
Actor(s) involved: Student (primary actor); System
Starting condition: The student is authenticated, the hostel accommodation application window for the cycle is currently open, and the student does not already hold an active application for the cycle.
Main sequence of activities:
●	The student opens the hostel accommodation application form.
●	The system displays the required fields - year of study, category and hostel/room preference.
●	The student fills in the application details and submits the application.
●	The system validates that the application window is open and that the student is eligible.
●	The system checks that the student does not already have an active application for the cycle.
●	The system creates the application record, displays a confirmation to the student, and sends an application notification.
Important alternative/exception flow: If the application window has already closed, the system rejects the submission and informs the student that applications are no longer being accepted. If 
the student already holds an active application for the current cycle, the system informs the student instead of creating a duplicate record.
Expected outcome: A valid application record exists for the student for the current allocation cycle, and the student has received confirmation of successful submission.
2.2. Scenario 2 - UC-006: Run Allocation
Actor(s) involved: Hostel Administration Office (primary actor); System; Hostel Warden
Starting condition: The application window has closed, the allocation criteria have been configured, and the hostel/room/bed inventory has been defined in the system.
Main sequence of activities:
●	The Hostel Administration Office initiates the allocation run.
●	The system retrieves all valid applications submitted for the cycle.
●	The system applies the configured allocation criteria against the available inventory and generates proposed allocation results.
●	The system presents the proposed results to the office for verification.
●	The office reviews and confirms the run.
●	The system stores the allocation results with status “Pending Verification”, ready for the hostel warden to verify.
Important alternative/exception flow: If the allocation criteria are not fully configured or the inventory is not ready, the system prevents the run and notifies the office rather than proceeding. If the available inventory is insufficient to accommodate every applicant, the system flags the unallocated applications for follow-up instead of failing the entire run.
Expected outcome: Allocation results exist for the cycle and are ready for warden verification and subsequent publication to students, with any applications that could not be accommodated due to insufficient inventory flagged for follow-up rather than left unresolved.

2.3. Scenario 3 - UC-011: Approve/Reject Room-Change Request
Actor(s) involved: Hostel Warden (primary actor); System; Student
Starting condition: The student holds an active room allocation, and a room-change/reallocation request submitted by the student is pending the warden's review.
Main sequence of activities:
●	The warden opens the pending room-change request.
●	The system displays the request details and the reason given by the student. 
●	The warden reviews the request against the currently available inventory and decides to approve or reject it.
●	If approved, the system checks availability of the requested room/bed, updates the occupancy records, reallocates the student, and marks the request as Approved.
●	If rejected, the system marks the request as Rejected.
●	The system sends a notification to the student informing them of the decision.
Important alternative/exception flow: If the warden approves the request but the requested room/bed is no longer available by the time it is processed, the system informs the warden, who may reject the request or select an alternative room instead. If the warden does not record a decision within the defined review period, the request remains pending (escalation is optional and configurable).
Expected outcome: The room-change request reaches a final status (Approved or Rejected), the occupancy records remain consistent with that outcome, and the student has been notified of the decision.

2. How the Classes Were Identified
The steps follow the standard class-identification approach:
·        Underline the nouns in the detailed use cases (Assignment 2, Section 8), the scenarios and the activity-diagram steps (Assignment 3).
·        Separate actions from things — e.g. Submit is an action while Application is the entity; Login is an activity, so it becomes an operation (User.login()) rather than a class.
·        Apply the four tests to every candidate: it becomes a class only if it (1) has information/data, (2) has its own identity, (3) has behaviour/responsibilities, and (4) has relationships with other concepts.
·        Keep only important attributes/operations — how much detail is actually needed. Create and Publish are different operations, so they are kept separate when both are needed.
·        Naming: classes use UpperCamelCase, attributes and operations use lowerCamelCase. Visibility: − for private attributes, + for public operations.
·        Not every actor becomes a class — only actors that behave as system users in the three use cases are modelled (Student, Hostel Warden, Hostel Administration Office).

4. Composition and Aggregation
Composition = strong whole-part: the part cannot exist without the whole and is deleted with it. Aggregation = whole-part where the part keeps an independent lifetime.
 
Figure 4 — Compositions (C1–C3, filled diamond) and aggregation (AG1, hollow diamond)
ID	Relationship	Justification
C1	Hostel ◆ Room (1 : 1..*), contains	A room is defined within a hostel (FR-007) and has no meaning without it; deleting a hostel removes its rooms. Every hostel has at least one room.
C2	Room ◆ Bed (1 : 1..*), contains	Beds exist only as part of a room and the number of beds equals the room's bed capacity, so a bed can never be allocated beyond capacity.
C3	AllocationCycle ◆ AllocationCriteria (1 : 0..1), hasCriteria	Criteria are configured for one cycle and are meaningless outside it. 0..1 because a cycle may not be configured yet; the run is then prevented (UC-006 alternative flow).
AG1	AllocationRun ◇ Allocation (1 : 0..*), produces	A run groups the allocations it generates, but an Allocation outlives the run: it stays with the student and is later changed by an approved room-change (UC-011). Hence aggregation (shared, independent lifetime), not composition.
 
Composition vs. aggregation in this model: Room and Bed disappear with their Hostel, so they are compositions. An Allocation, however, is produced by an AllocationRun but lives on after the run — it is published, held by the student and later changed by an approved room-change — so it is only an aggregation.

A8	RoomChangeRequest 0..* — raisedBy — 1 Student	Each request is raised by exactly one student; only one may be pending at a time (AC-02 of US-009).
A9	RoomChangeRequest 0..* — concerns — 1 Allocation	The request concerns the student's current allocation, re-pointed to the new bed on approval.
A10	RoomChangeRequest 0..* — requestedRoom — 1 Room	The room the student asks for; the warden reviews it against currently available inventory.
A11	RoomChangeRequest 0..* — decidedBy — 0..1 HostelWarden	0..1 because a pending request has no approver yet; exactly one warden once decided.
A12	HostelWarden 1..* — manages — 1..* Hostel	A hostel has one or more wardens assigned and a warden may look after more than one hostel.
A13	User 1 — receives — 0..* Notification	Every notification has one recipient: student, warden, or office. Modelled on User so all roles are covered.
 

6. Dependencies
Dependencies (dashed arrow with stereotype) are used where a class only uses or creates another temporarily and does not keep a permanent reference to it.
 
Figure 6 — Dependencies D1–D9
ID	Client → Supplier	Justification
D1	AllocationRun → AllocationEngine «use»	The run delegates matching to the engine (steps 'apply criteria' and 'generate proposed results').
D2	AllocationEngine → Application «use»	Reads the valid applications retrieved for the cycle.
D3	AllocationEngine → AllocationCriteria «use»	Uses the configured criteria to score and order applicants.
D4	AllocationEngine → Bed «use»	Looks up vacant beds in the available inventory; it changes no Bed itself.
D5	AllocationEngine → Allocation «create»	Instantiates the proposed Allocation objects.
D6	Application → NotificationService «use»	After creating the record the system sends an application notification.
D7	RoomChangeRequest → NotificationService «use»	After a decision the system sends a decision notification (UC-011 includes UC-014).
D8	AllocationRun → NotificationService «use»	When criteria/inventory are not ready the system prevents the run and notifies the office.
D9	NotificationService → Notification «create»	Instantiates the Notification that is delivered to the recipient.
 
NotificationService is a dependency rather than an association on purpose: Application, RoomChangeRequest and AllocationRun just call it, mirroring the <<include>> of UC-014 in the Assignment 3 use case model. The persistent link is User 1 --- 0..* Notification (A13).

7. Key Design Decisions
Rule	Enforced By
BR-002 One active application per student per cycle	A1 + A2, Student.hasActiveApplication(cycle), Application.isActive()
BR-003 Applications only inside the window	A2, AllocationCycle.isWindowOpen()
BR-004 Allocation only after the window closes	A6, AllocationRun.checkReadiness() (cycle status = Closed)
BR-005 Never allocate beyond capacity	C2 (Room 1 – 1..* Bed), A5 (Bed has at most one Allocation)
BR-006 One active allocation per student	A4 (Student 1 – 0..1 Allocation)
BR-007 Room change needs warden approval	A11 + HostelWarden.approveRequest(); RoomChangeRequest is Pending until decided
BR-008 Occupancy updated immediately	Allocation.reallocate() calls Bed.markVacant() / Bed.markOccupied() in one operation
